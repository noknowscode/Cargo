# The black frame after a live resize to 599 (2026-11-04)

Re-tested on `feat/production-readiness` (after bc72e6e), Uno.Sdk 7.0.0-dev.115 (Uno.WinUI 7.0.0-dev.2509), Debug
`net10.0-desktop`, Xvfb display `:466` at 24-bit, X11 host. **It reproduces, on the OpenGL path only.**

## Method

The app is started on Waterways with `CARGO_WINDOW=<w>x800`, `CARGO_START_SECTION=fleet` and `CARGO_SCROLL=<y>`, left
to settle 13-14 s, then resized live with `xdotool windowsize <win> 599 800` (or in 20 px steps), and captured 4 s
later with `import -window`. A frame counts as black when more than half its pixels are below 4% grey. Each condition
was run 2 to 6 times. The OpenGL path is the default X11 renderer (Mesa llvmpipe here); the CPU path is
`CARGO_X11_RENDERER=software`.

## Results

| Condition | Black |
|---|---|
| CPU renderer, 1280, 1000 or 640 to 599, scrolled 600, one jump (2 runs each) | 0 of 6 |
| CPU renderer, 640 to 599 in 20 px steps, scrolled 600 | 0 of 1 |
| GL, 640 to 599, scrolled 600 | 5 of 5, 2 of 3, 1 of 2 (three batches) |
| GL, 700 to 599, scrolled 600 | 2 of 3 |
| GL, 1280 to 599 in 20 px steps, scrolled 600 | 1 of 1 |
| GL, 1280 to 599 in one jump, scrolled 600 | 0 of 1 |
| GL, 640 to 599, not scrolled | 0 of 3 |
| GL, 640 to 599, scrolled 1200 (the river map out of view) | 0 of 5 |
| GL, opened at 599 and scrolled 500, 600 or 700, no resize | 0 of 6 |
| GL, resizes that do not cross 600 (700 to 620, 640 to 610, 1100 to 1000, 1000 to 900) | 0 of 12 |
| GL, Overview 640 to 599 | 0 of 1 |

Once black, the window stays black at 599 (8 s later, still black), comes back on a resize to 620, and goes black
again on the way back to 599. Only two small paths survive in the black frame (`2026-11-04-black-frame-599-gl.png`, the
water-level sparklines); the CPU path draws the same state correctly (`2026-11-04-black-frame-599-cpu.png`).

## What narrows it down

- **The river map is needed.** With a temporary switch that put a text block in place of `RiverMap` the frame never
  went black (0 of 9); with the river map reduced to its three background rectangles it still did (1 of 3), so no one
  drawing in it (the gradient channel, the dashes, buoys, gauges, locks, notices, boats) is the trigger.
- **Crossing the 600 breakpoint is needed.** Resizes inside one size class never fail; crossing 1000 does not either.
  At 600 the page padding, the tile widths and the header rows switch together in the same frame as the resize.
- **The river map's own layout is sane.** A temporary trace of `SceneHost.ArrangeOverride` gives 567 x 158 at 599 in
  every failing run: no zero or NaN scale.
- **No error is reported.** `MESA_DEBUG=1 LIBGL_DEBUG=verbose` print nothing after the resize; the app logs nothing.

## Conclusion

The fault is in the X11 OpenGL renderer under Xvfb (Mesa llvmpipe): a frame drawn after a live resize across the 600
breakpoint, with a scaled `Canvas` scene in view, comes out black, while the CPU renderer draws the same visual tree
correctly. No app code is implicated: the trigger needs only a `ScaleTransform`ed `Canvas` of rectangles in view, and
its layout is correct. Two investigation cycles (part bisection, then the scene's arrange) did not reach a fix in the
app, so it stays a renderer issue: the verification runs on this box use `CARGO_X11_RENDERER=software`, and the
Windows, macOS and GPU Linux heads are not affected as far as this test can say (not run here). Next step if it
matters: reduce it to a two-element repro (a `ScrollViewer` holding a scaled `Canvas` and a `{utu:Responsive}` value
that changes at 600) and report it to Uno.
